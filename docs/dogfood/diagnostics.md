# GitReins — Diagnostic Trail (how it's built, errors hit, the right way)

> "Not raw logs — explanation." This file explains how GitReins is built, why it's
> built that way, the errors encountered along the way (both the project's own history
> and this dogfood run), and the right way to use each piece.

## What GitReins is, and why it's shaped this way

GitReins is a **git-native quality harness**: it lives INSIDE a repo (`.gitreins/`,
a pre-commit hook) rather than in CI. The design bet is that AI agents (Claude,
Hermes, Codex, Pi) do the bulk of coding, so the harness targets agent workflows:
tasks with explicit completion criteria, an LLM evaluator that judges the work, and
Tier-1 static gates that run on every commit.

Architecture (see `specs/` for the originals):
- `gitreins/cli.py` — CLI entry (install/init/task/guard/judge/commit/mcp-server/
  security-scan/setup-tools/report).
- `gitreins_mcp/server.py` — MCP stdio server exposing the same operations as tools
  (task_create/start/complete, judge_evaluate, guard_run, commit, configure,
  propagate).
- `engine/guard_manager.py` — Tier 1: `_check_secrets` (gitleaks first, built-in
  regex scanner fallback), `_check_lint` (ruff/flake8), `_check_tests` (full or
  diff-mode via basename mapping; unknown files or config changes → full suite).
- `engine/evaluator.py` — Tier 2 agentic evaluator: an LLM loop that reads files,
  runs commands, and produces per-criterion PASS/FAIL verdicts. Capped by
  `evaluator:` config (iterations/time/tokens) and overridable via
  `GITREINS_MAX_*` env vars (highest priority).
- `engine/llm.py` — LLM client. Env: `GITREINS_LLM_BASE_URL`, `GITREINS_LLM_API_KEY`,
  `GITREINS_LLM_MODEL`, `GITREINS_LLM_PROVIDER` (openai|anthropic auto-detect).
  Falls back to `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY`.
- `.gitreins/tasks.yaml` — local task state (never committed).
- `.gitreins/history/` — verdict history, git-stored, browsable via `gitreins report`.
- Config: `.gitreins/config.yaml` — guards (secrets/lint/tests/test_mode/
  test_command/test_timeout), evaluator caps, defaults (model).

## Errors encountered on THIS run (2026-08-03) and the right way

### 1. gitleaks panic: invalid allowlist regexes generated by `gitreins init`

**How it's built:** `_generate_gitleaks_config()` in `gitreins/cli.py` writes a
`.gitleaks.toml` with an `[allowlist] paths = [...]` list that mixes directory
globs (`docs/`, `.venv/`) with regex-ish patterns (`*.log`, `*.md`, `*.spec.md`,
`*.egg-info/`). gitleaks compiles EVERY allowlist path as a Go regexp, so `*.log`
(no atom before `*`) panics the process. `_check_secrets()` runs gitleaks first;
only `FileNotFoundError` (binary missing) triggers the built-in scanner fallback —
a panic exit code does NOT.

**Error seen:**
```
✗ secrets — ○
panic: regexp: Compile(`*.log`): error parsing regexp: missing argument to repetition operator: `*`
```
(the `○` is gitleaks' ASCII logo — the guard surfaces the panic dump as the result)

**Right way:** allowlist entries must be valid regexes: `.*\.log`, `.*\.egg-info/`,
`.*\.spec\.md`, `.*\.md`. Fix in `gitreins/cli.py` (the generator), not just in one
repo's config. Until fixed: delete the generated `.gitleaks.toml` (built-in scanner
takes over) or hand-fix the four entries.

### 2. Bare `pytest` can't import the root package (pytest 9 importlib mode)

**How it's built:** generated `test_command: pytest -x --tb=short` runs through a
shell. A bare `pytest` script does not add cwd to `sys.path`; pytest 9 defaults to
importlib import mode, so `tests/test_x.py` doing `from mypkg import ...` fails with
`ModuleNotFoundError` even though `python3 -m pytest` passes. `_check_tests` then
reports `✗ tests (full)` and the commit is blocked for a reason the user cannot
reproduce.

**Right way:** for root-package layouts use `[pytest] pythonpath = .` in
`pytest.ini`/`pyproject.toml`, or set `test_command: python3 -m pytest -x --tb=short`,
or install the package (editable) into the environment. The generator should
probably probe (`python3 -m pytest` vs `pytest`) or document this in the init output.

### 3. Guard output truncation hides failure context

**How it's built:** `_run_test_command` keeps only the last 2000 chars of captured
output; on failure the CLI prints `✗ <name> — <first line of output>`. For pytest
the first line is `=== test session starts ===`, so the actual error is invisible
in the guard summary.

**Right way:** run `python3 -m pytest -x --tb=short` yourself to see the failure.
(Maintainers: print the FAILURE tail, not the head, in the summary.)

### 4. `init` reports `Language: unknown` for plain-Python repos

Language detection keys off pyproject.toml/setup.py presence; a repo with only
`.py` files and tests reports `unknown` and skips Python-specific tuning
(test_mode stays `full`, no venv/`__pycache__` gitleaks exclusions... actually
those ARE added only when `is_python`; with `unknown` they are NOT). Right way:
add a `pyproject.toml` before `gitreins init`, or make detection fall back on
`.py` file presence.

## Errors the PROJECT hit historically (from git history / tasks board)

- **`os.kill()`/`os.killpg()` without PID validation** — `int(mock.pid) == 1` killed
  init; took down Kara's session every 2–5 min for 30+ hours. AGENTS.md now mandates
  `isinstance(pid, int) and not isinstance(pid, bool) and pid > 1`. See
  `engine/lsp.py:408-428`. Lesson: never trust mock/passed PIDs; validate before kill.
- **DeepSeek HTTP 400**: per-request `max_tokens` used to send the whole session
  budget; fixed with `max_tokens_per_call` (default 16384) — v0.10.1.
- **Evaluator timeout loops on slow suites**: judge Tier 1 kept timing out on the full
  suite (CI ~11m) with `test_timeout: 360`; raised to 900 and evaluator iterations
  100→200 (commit 8205127). Lesson: guard timeouts must exceed suite runtime.
- **GR-099 blocked (pydantic 2.13.4 pins core==2.46.4)** — long-running type-annotation
  project blocked by a dependency pin; foreman re-verifies periodically. Lesson:
  dependency-pin blocks need an unpin task or a version floor bump, not repeated
  re-verification.
- **GR-137 tier2 cap forwarding**: step caps were merged over config base in a
  compaction loop (int(-1*0.9)=0 guard); fixed so explicit step caps parse string
  tokens ('200k') and defer to config base when unset.
- **Static analysis disabled 2026-07-19**: 2150 pre-existing mypy --strict errors;
  re-enable after GR-099. Documented in `.gitreins/config.yaml`.

## The right way to use GitReins (condensed)

1. **Before `gitreins init`:** have `pyproject.toml`/`setup.py` present, a venv with
   your deps installed, and a `.gitignore` that covers `__pycache__/`, `.venv/`.
2. **Fix the generated `.gitleaks.toml`** (invalid regexes, see above) or delete it.
3. **Make tests runnable via bare `pytest`** (`pythonpath = .` or editable install).
4. **Workflow:** `gitreins task create <id> <title> <criteria...>` →
   `gitreins task start <id>` → do the work → `gitreins task complete <id>` (LLM
   judge) → `gitreins commit` / plain `git commit` (hook runs guards) → `gitreins
   report` to browse verdicts.
5. **Never commit `.gitreins/tasks.yaml`** (local state). Verdicts are already
   git-stored under `.gitreins/history/`.
6. **AI agents:** use the MCP tools (`task_*`, `guard_run`, `judge_evaluate`,
   `commit`) — same semantics as the CLI; the `commit` tool runs guards first and
   rejects if they fail.
